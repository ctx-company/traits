# 0078.4 — Decide autostash for the dirty-overlap remainder

**Status:** filed, not scheduled (owner decision — captured so the research is not lost,
deliberately not queued) · **Depends on:** 0078.1, plus live park data · **Raised:** 2026-08-04
(split from 0078's research section)

0078 ordered the dirty-main work deliberately: measure the overlap case, narrow the check, THEN
decide autostash. The harvest (0078.1) lands the narrowing — a landing that does not touch the
checkout's dirty files proceeds unstashed, and overlapping staged/unstaged/untracked work is
refused without mutating the owner's tree. What remains is only the decision: is the refused
remainder frequent enough to be worth `git merge --autostash` and its pop hazard?

Findings carried from 0078, both checked rather than assumed:

- **The standing "never `git stash` in this repository" rule does NOT apply to `--autostash`.**
  That rule exists because `refs/stash` is shared repo-wide. Autostash records its entry in
  `MERGE_AUTOSTASH`, which is per-worktree (`.git/worktrees/<id>/MERGE_AUTOSTASH`; git 2.47.1,
  `git rev-parse --git-path`). The usual objection is answered.
- **The real hazard is the pop, and it lands in the owner's tree.** git's own manual says the final
  stash application "might result in non-trivial conflicts". A background landing that leaves the
  owner's uncommitted work conflicted is worse than the park it replaced — not acceptable at any
  frequency, so it must be designed for: on a conflicting pop, restore the pre-merge state, keep
  the landing, and say plainly where the stashed work is (the entry survives in `MERGE_AUTOSTASH`
  for exactly this).

Decide from live evidence after 0078.1 has been landing for a while: if overlap refusals stay rare,
close this as not-worth-it and record that; if they recur, implement autostash for the overlap
remainder with the conflicting-pop design above.

## Phase A — decision procedure (this round)

**Counting is now mechanical.** `FAST_FORWARD_FAILED` used to conflate the dirty-overlap refusal
("Your local changes to the following files would be overwritten by merge" / "The following
untracked working tree files would be overwritten by merge") with the lost-race non-fast-forwardable
history refusal ("Not possible to fast-forward, aborting"), so a tally required reading the raw git
diagnostic out of each park frame by hand. `merge.rs`'s `--ff-only` failure handler now inspects the
git error text at the moment of refusal and persists one of two distinct reasons to the ledger:
`ParkClass::LandingDirtyOverlap` (new) for the overlap signature, `ParkClass::LandingFastForwardFailed`
(unchanged) for everything else — see `modules/cli/src/app/merge_story.rs` (`reasons::LANDING_DIRTY_OVERLAP`,
`classify_reason`) and `modules/cli/src/app/merge.rs` (~line 2194). No merge behavior changed: both
refusals still retry identically (`ParkDisposition::Race`), and disjoint-dirty landings are untouched
— only the persisted classification is more specific. Verified empirically (scratch repo, git 2.47.1):
a dirty-overlap refusal (tracked or untracked) always contains "would be overwritten by merge"; a
diverged-history refusal never does. Proof coverage: `modules/cli/tests/proof_merge_on_completion.rs`'s
`overlapping_dirty_checkout_work_is_refused_without_mutation` already exercises the overlap path
end-to-end (still green); `merge_story.rs`'s
`dirty_overlap_and_fast_forward_failed_classify_distinctly` unit-tests the split directly.

**Proposed decision criterion (owner's call to confirm or adjust):** review after a bounded
observation window — two weeks of live landings, or ~30 landings, whichever comes first, counted
from whenever this split starts landing on `main`. Tally `ParkClass::LandingDirtyOverlap` parks
across that window's session ledgers. Zero or one genuine occurrence → close this task as
not-worth-it, record the count here. Two or more distinct occasions → schedule Phase B (autostash),
using the implementation shape and mandatory conflicted-pop probe already on file in the round-1
draft (`.internal/tasks/0078.4-decide-autostash-for-the-overlap-remainder.md` history / the
implementation draft this task ran from).
