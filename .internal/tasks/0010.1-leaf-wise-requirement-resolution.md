# 0010.1 — Requirement resolution must be leaf-wise, driven by classified metadata

**Status:** ready to implement · **Raised:** 2026-08-03 (split out of 0010 after run-a3e5fc88 parked at max-iterations with five open blockers; 0010's design decisions are LANDED — these are the implementation remainder)

Carried from blocker `requirement-resolution-loses-leaf-presence` (3/6 steps done).

## What already landed

Requirement-conflict diagnostics are generated from classified leaf metadata rather than the old
eight-field hand-written list, and are emitted only when the rejected declaration actually differs
from the repository requirement. Each requirement resolves to ONE effective repository source
before `$CTX_CONFIG` is compared, so a rejected declaration produces exactly one diagnostic naming
the winning document — proven by a test with conflicting legacy and current repository config paths.

## Remaining

- Introduce typed per-leaf semantic and authored-presence metadata, with a schema-coverage test
  that FAILS when any authored `RuntimeConfig` leaf lacks a classification. The coverage test is
  the point: classification that can silently miss a field is the defect 0010 exists to remove.
- Replace post-merge whole-structure restoration with leaf-wise requirement resolution across every
  requirement family: schema-version, worktree, run-budget, run-policy, merge.
- Tests for explicit default-valued repository requirements, partial nested requirement tables,
  ordered-list requirements, every requirement family, and unchanged fallback behaviour.

## Done when

`cargo test -p ctx-traits-io harness_config` and `cargo test -p ctx-traits-cli --test proof_config`
pass with tests proving every classified requirement family survives a conflicting `$CTX_CONFIG`
without displacing the repository value, and the schema-coverage test fails when a leaf is left
unclassified.
